# 標準 V9968 カートリッジ上の geo3d：検証レポート

日付：2026年9月27日。ベース：HRA! 氏のカートリッジプロジェクト（Tang Nano 20K、Gowin GW2AR-18C FPGA）のバージョン 86361d8 に、スクリプト `geo3d/integration/apply_geo3d_patch.py` で geo3d を統合したものです。ブランチは `geo3d-phase2` です。この段階の変更はまだ何もコミットしていません（12 章）。

## 3. 基板（ハードウェア）

**結論：標準のカートリッジは、何も変更せずに geo3d に対応できます。** クロックの修正（4 章）は FPGA のみです。

- **アドレス：** A0-A7 は U5（SN74LVC8T245、DIR は GND、入力専用）を経由して FPGA に届きます。A8-A15、/SLTSL、/MERQ、/M1 は届きません。このカートリッジは I/O 専用で、ROM は別のスロットにあります。
- **制御：** /IORQ、/RD、/WR、/RESET は U6（DIR は GND）を経由します。
- **データ：** U4 の方向は FPGA が制御します（`SLOT_DATA_DIR`、R2 による 10k のプルダウン付き）。
- **/BUSDIR：** Q1（オープンドレインの NMOS）から出力され、ゲートは同じ `SLOT_DATA_DIR` につながっています。カートリッジがバスをドライブしている間は、どのポートでも Low になります。
- **/WAIT：** Q2 を経由し、起動時（FPGA のコンフィギュレーションと SDRAM の初期化が終わるまで）だけ使われます。geo3d は /WAIT を使いません。
- **デコード：** オリジナルの `msx_slot.v` はすでに 8 ポートのブロック全体（DIP スイッチにより 88h-8Fh または 98h-9Fh）をデコードしています。VDP は +0 から +4 を、geo3d は +5（インデックスとステータス）と +7（データ）を使います。+6（8Eh）は意図的に使っていません。
- **リード：** geo3d のリードは VDP のステータスリードと同じ経路を通り、U4 の方向切り替えも /BUSDIR も同じです。
- **シミュレーション上の応答時間：** geo3d は /RD から 116 から 140 ns 後にデータをバスに出します（clk42g でのシミュレーションでは 139.7 ns）。3.58 MHz の Z80 は約 500 ns 後に読むので十分な余裕があり、7.16 MHz でも約 220 ns の余裕が残ります。レベル変換器の遅延はこの計算に含まれていません。

**お手元の機材で確認していただきたい点：**
- **MegaRAM：** msx.org のポートマップ（再確認はしていません）によると、8Eh-8Fh は MegaRAM が使用します。アドレスを一部しかデコードしない MegaRAM は、8Fh での geo3d のリードに反応する可能性があります。
- **水晶：** 基板の部品表（`pcb/.../parts.txt`）では U1 は 28.636 MHz となっていますが、プロジェクトの PLL は 14.318 MHz を前提としています。どちらが実装されているか確認する価値があります。これは HRA! 氏のオリジナルのビットストリームにも同じように当てはまります。
- **電源：** Tang Nano の 5 V ピンはスロットの +5 V に接続されています。**ビットストリームの書き込みは、カートリッジを MSX から抜いた状態で行ってください。**

## 4. HRA! 氏のプロジェクトで変わる点

すべて `apply_geo3d_patch.py` で適用します。このスクリプトは冪等で、HRA! 氏のソースのテキストが変わっていればエラーで停止します。実行のたびに、すでに変更済みのツリー（たとえば HRA! 氏の更新をマージした後）であっても、rPLL2 の設定、`u_pll2` の接続（入力 clk14m、出力 clk85m）、SDC のクロックとマージンを確認します。いずれかの確認に失敗した場合は、何も書き込みません。クリーンな 86361d8 に適用すると、リポジトリの `fpga/` ツリーを正確に再現します（本日あらためて確認しました）。

|---|---|---|
| `src/v9968/vdp.v` | +11 / -3：コマンドレジスタへの外部書き込みポート（`ext_cmd_wr/num/data`）を CPU からの書き込みに加え、CE を出力 | geo3d が停止している状態では、VDP はオリジナルと**同一**です。形式検証（695 点中 695 点、86361d8 では 697 点中 697 点）と、全ピンが一致した 360 万サイクルの並列シミュレーションで確認 |

- 52 の表は、clk85m、clk42m、clk42g、clk215m、clk の 25 のペアそれぞれのセットアップとホールド、それにリカバリとリムーバルです。最終ビルドでは、そのうち 38 の表にパスがありません。clk215m または clk を含むすべてのペア（32 表）、clk42m と clk42g の間のペア（4 表、HDMI と geo3d はつながっていないため）、clk42m から clk85m へのペア（2 表）です。
- clk85m と clk42g の間のスラックは、0.5 ns のマージンを差し引いた後の値です。マージンがなければ、このクロスのホールドは約 +0.54 ns になります。
- **Gowin のレポートを読む際の注意：** 「Total Negative Slack」のサマリーは、クロック間のパスが違反していても 0 と表示します。違反が見えるのはパス表だけです。`build_gowin.sh` はこれらの表を生成し、すべてを確認します。

**以前の違反の原因：** clk42m は CLKDIV 分周器から出ており、Gowin のモデルでは遅延がゼロですが、PLL から出る clk85m には 2.9 から 4.4 ns の遅延があります。geo3d のクロックドメイン間の受け渡しは、クロックがそろっていることを前提としています。

**適用した修正：** geo3d に clk42g を追加しました。clk85m と同じ PLL の CLKOUTD 出力（CLKOUT / 2）です。これにより、モデル上で geo3d のクロスのクロックスキューは 0 ns になりました（以前は 4.36 ns）。

**0.5 ns のマージン：** Gowin は CLKOUTD に CLKOUT とまったく同じ遅延を与え、分周器そのものの遅延はモデル化していません。SDC は clk85m と clk42g の間の両方向に 0.5 ns（`set_clock_uncertainty`）を確保しています。**この値は仮定であり、測定値ではありません。** ロジックを確認するため、clk42g を 0.5 ns と 2.0 ns 遅らせたシミュレーションも行いました（7 章）。

- セットアップ 85 → 85：+0.058 ns。VDP のコマンドエンジン内のパスです（オリジナルでは +0.111 ns、clk42m のビルドでは +0.031 ns）。このスラックは配置によって変わります。

## 7. 統合 RTL のシミュレーション

iverilog で、HRA! 氏のトップ全体（クリーンな 86361d8 に最終スクリプトを適用したもの、リポジトリと同じ Verilog）を、VDP、スロット、SDRAM コントローラ、Micron MT48LC2M32B2 モデル、それに geo3d を含めて 85.909 MHz でシミュレーションしました。スタブは PLL、分周器（実際に 2 分周します）、HDMI だけです。PLL のスタブは `clkoutd` を clk85m / 2 として同相で生成します。チェッカー（`clkcheck.v`）が、geo3d の `clk_eng` が clk42g であること、正確に半分の周波数であること、ずれたエッジが 0 であることを確認します。Z80 側は OTIR の速度で実際の I/O サイクル（/IORQ、/RD、/WR、A0-A7、D0-D7）を使います。VRAM（256 KB）は、書き込みの抜けを検出できるよう、擬似乱数パターンで埋めた状態から始めます。

| テスト | 結果 |
|---|---|
| レジスタ、ステータス、即時変換 | エラー 0 |
| ワイヤーフレーム（立方体と正八面体、XOR と TIMP） | VRAM 一致 |
| シェーディングしたソリッド面 | VRAM 一致 |
| テクスチャ付きの面（LRMM） | VRAM 一致 |
| 実際のテクスチャデモ（GEO3DT.COM）、すべての OUT を再現 | 2,842 コマンド（LINE 1,855、LRMM 987）、相違 0、3 フレーム一致 |
| DIP スイッチ 98h | 合格 |
| 起動時の状態（V9958 モード） | VRAM 一致 |
| geo3d から VDP への 39,158 回の書き込みでのハンドシェイク | CE = 1 での書き込み 0、抜け 0、衝突 0 |
| 意図的な競合：geo3d がビジーの間に CPU が R#32-R#58 に書き込む（33 回） | 同一サイクルでの衝突 4 回とフレームの破損、想定どおりです。9 章のルールを裏付けます |

- **旧クロックおよび前回の納品物との比較：** コマンドログとリードログ、VRAM、サイクル数は、clk42m でのシミュレーションとも、clk42g を使った前回の納品物とも、バイト単位で一致しました。起動時の状態のテストは以前は clk42m でしか実行していなかったため、今回の見直しで最終ツリー上で再実行しました。
- **遅延させたクロック：** 7 つのテストを、clk42g を clk85m に対して 0.5 ns と 2.0 ns 遅らせて実行しました（14 回）。ゲート遅延のないシミュレーションでは、これにより clk85m から clk42g へのすべての取り込みが、同じエッジで送出された値を取り込むことになります。14 回すべて合格しました。VRAM はクロックがそろった場合と一致しました。例外は意図的な競合テストで、衝突が変わり（4 回ではなく 1 回）、それに伴って破損したフレームも変わります。
- **限界：** シミュレーションは実際の配線遅延をモデル化していません。それはタイミング解析（6 章）と実機のカートリッジに委ねられます。

## 8. HRA! 氏のオリジナルのビットストリーム（geo3d なし）での当方のソフトウェア

| プログラム | 動作 | 状況 |
|---|---|---|
| BASIC ROM（G3BASIC.ROM） | 起動表示「geo3d BASIC 0.2 (none)」。`CALL G3INIT` は「Device I/O error」になり、BASIC はそのまま動作し続けます | 正しい |
| ゲーム VECTOR RAID | 止まりはしませんが、自機も敵も表示されないまま、警告なしで動作します | 許容範囲 |
| デモ ROM | 「geo3d not found」画面（英語、スペイン語、ポルトガル語）を表示し、そこで停止します。geo3d のどのポートにも書き込みません | **正しい（修正済み）** |

**デモ ROM が geo3d を検出する方法**（`geo3d_rom.asm` の `geo_probe`。BASIC ROM の `detect` と同じ方法で、ROM 自身のベースアドレスでのみ行います）：
1. 98h 版の ROM は、MSX1（MSXVER = 0）では何もしません。TMS9918 は R#15 への書き込みを R#7 として解釈してしまうためです。
2. S#1 から VDP の ID を読みます。ID 0、2、3 は V99x8 があることを意味し、メッセージの画像をそこに表示できます。geo3d には ID 2 または 3 が必要です。
3. R#15 = 2 にして P+5 を読みます。FFh（HRA! 氏のビットストリーム、または空きポート）は geo3d なしを意味します。ビット 3-2 = 11 は、ポートが P+4 から P+7 に繰り返し現れる VDP を意味します。その後で初めて PORT#4 を読みます。
4. geo3d への最初の書き込みはインデックス 40h です。続いて P+7 を 17 回読み、17 回目の値は 1 回目と同じでなければなりません。

検出は 29 回のポートアクセスで行います。geo3d がある場合、その後のトラフィックは以前の ROM と同一です。

**geo3d がない場合：**
- ベースアドレスに V99x8 がある場合は、メニューと同じスタイルの SCREEN 5 の画像を表示します。どの V99x8 でも受け付けるレジスタだけを使い、V9968 のレジスタ、コマンド、PORT#4 への書き込みは一切使いません。
- 88h 版の ROM は、BIOS（INITXT と CHPUT、プレーンな ASCII）で MSX 本体の画面にもテキストを表示します。88h に V9968 がない場合は、これが唯一のメッセージです。98h 版は MSX1 の場合にのみこれを行います。
- ROM は割り込み禁止のループ（`ng_stay`）にとどまります。
- **50/60 Hz：** 98h 版の ROM は本体の周波数を維持します（R#9 = `(RG9SAV & 02h) | 80h`、PAL 機では 82h）。88h 版はカートリッジの HDMI のため 80h（60 Hz）を使います。

**待ちのタイムアウト：** geo3d の RUN と VDP の CE の待ちは、3.58 MHz の Z80 で約 3 秒後に打ち切られます（シミュレーターでは 3.08 から 3.29 秒）。turbo R では、カートリッジの INIT は Z80 で動作します。R800 の ROM モードでは、待ちの 65,536 回のリード 1 周（Z80 では約 1.6 秒）に約 0.7 秒かかります（レビュー時の測定値で、再測定はしていません）。タイムアウトになると（`hw_timeout`）：
1. 音楽を止めます。
2. コマンドエンジンに STOP（R#46 = 0）を送ります。
3. 描画中のフレームがメッセージの上に描かれないよう、geo3d の RUN が終わるのを、P+5 を最大 32,768 回読んで（約 0.55 秒）待ちます。
4. RUN が終わった場合に限り、2 回目の STOP を送ります。
5. 同じメッセージを表示します。

|---|---|---|

## 9. geo3d をプログラムする方へのルール

- geo3d の描画中（RUN がビジーの間）は、**R#32 から R#58** に何も書き込んではいけません。LRMM は R#47 から R#58 を使い、geo3d の書き込みと同じサイクルで行われた CPU の書き込みは失われます。7 章の意図的な競合テストがこれを示しています。
- **CE = 0 はエンジンが空いていることを意味しません。** CE は geo3d のあるコマンドと次のコマンドの間で下がります。geo3d のステータスのビット 0 を待ってください。
- LRMM のウィンドウ（R#51 から R#58）は VRAM 全体をカバーしている必要があります。これはリセット時の値です。

これらのルールは `BASIC_API.md` の 7.2 節に記載しています。3 つの ROM はすでにこれを守っています。唯一の例外はデモ ROM の `hw_timeout` の STOP ですが、それも理論上だけです。geo3d は、固まっている場合でも、CE が High の間はレジスタに書き込みません。

1. **geo3d のビットストリームの書き込み**は、**カートリッジを MSX から抜いた状態で**、USB-C で PC に接続して行います。事前に SHA-256 を確認してください。
   - Gowin Programmer：デバイス GW2AR-18C、Access Mode = External Flash Mode、Operation = exFlash Erase,Program thru GAO-Bridge、ファイル `geo3d_cartridge_86361d8.fs`。

2. **最初の起動：** USB ケーブルを抜き、DIP スイッチを 88h にし、MSX の電源を切った状態でカートリッジをスロットに挿し、HDMI を接続してから MSX の電源を入れます。通常どおり起動するはずです。起動せずに固まった場合は、/WAIT がアサートされたままです。FPGA のコンフィギュレーションができなかったか、SDRAM が初期化されなかったことを意味します。電源を切り、カートリッジを抜いて、もう一度書き込んでください。
3. **最初は BASIC ROM** です。最も安全だからです。geo3d を識別するまではリードしか行わず、待ちにはタイムアウトがあり、CTRL+STOP も受け付けます。起動表示に「(88h)」と出るはずです。次にサンプルを実行します：`10 SCREEN 5:CALL G3INIT`、`20 CALL G3OBJ(1,1)`、`30 CALL G3SPIN(1,1,2,0)`、`40 CALL G3FRAME:GOTO 40`。

5. **最後にデモ ROM**（`GEO3D_88_hardware_real_MOD.ROM`）：言語メニューとデモです。

   - デモの途中で同じメッセージが出る場合：geo3d またはコマンドエンジンが約 3 秒間応答しなくなりました。デモの名前と発生したタイミングを記録してください。調査すべき実際の問題です。
6. **観察する点：** 描画中の点やゴミ（SDRAM）、数分後のフリーズ、発熱。可能であれば、PAL 機や turbo R を含むほかの MSX 機種でもテストしてください。
